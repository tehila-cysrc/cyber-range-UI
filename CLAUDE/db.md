# DB

SQLite via Node's built-in `node:sqlite` (`DatabaseSync`) — see `CLAUDE/services.md` for why this replaced the originally-planned `better-sqlite3`. File: `server/data/cyber-range.db` (gitignored), path from `.env` `DB_PATH` (relative to `server/`).

## Schema philosophy: CONFIG vs RUN

Schema is split into two files, applied in order by `server/src/db/migrate.ts`:

- **`server/src/db/schema/config.sql`** — reusable content. **Never touched by the event-reset operation.** `days`, `cyber_ranges`, `pressure_stages`, `documentation_categories`, `topology_zones`, `topology_nodes`, `topology_edges`, `scoring_config`, `credentials`, `cloud_environments`, `cyber_range_environments`, `audit_log`, `environment_discovery_runs`, `access_targets`, `scripts`.
- **Additive columns on `topology_nodes`/`topology_edges`** (`environment_id`, `discovery_run_id`, and on edges also `external_key`/`relation_type`), **`topology_nodes.zone_id`/`role`/`is_visible_to_students`/`status`** (the logical-topology redesign — see below), **`documentation_entries.image_data_url`** (optional base64 `data:image/...` screenshot attached to a finding), and **`cyber_ranges.is_active`** (defaults `1`; see below) are applied by `server/src/db/migrate.ts` via an idempotent `addColumnIfMissing` helper, not as raw `ALTER TABLE` statements in the `.sql` files — SQLite has no `ADD COLUMN IF NOT EXISTS`, and `migrate()` must stay safe to re-run. If you need another additive column later, follow this same pattern rather than adding a bare `ALTER TABLE` to `config.sql`/`run.sql`. **Exception**: `topology_edges.from_node_id`/`to_node_id` had to change from `NOT NULL` to nullable (to allow a zone-boundary edge endpoint) — SQLite can't relax a column constraint via `ALTER TABLE`, so `migrate.ts#relaxTopologyEdgesForZones` rebuilds the table once (create-new/copy/drop/rename), guarded by checking for the `from_zone_id` column so it's a no-op on an already-migrated database.
- **`server/src/db/schema/run.sql`** — per-event data. **Wiped by `POST /api/admin/event/reset`** (not yet built — planned Phase 9). Everything cascades from `event_runs` via `ON DELETE CASCADE`: `event_runs`, `teams`, `users`, `auth_tokens`, `team_cyber_range_progress`, `documentation_entries`, `scores`, `help_requests`, `access_sessions`, `script_executions`.

> **Invariant:** no CONFIG table may ever gain a foreign key into a RUN table. This is what makes the reset operation safe by construction — if you're adding a new table, decide CONFIG vs RUN first and put it in the matching file.

## Key relationships

- `cyber_ranges.day_id -> days.id` — the reusable scenario catalog (seeded from PRD §9: AI/TJS advanced 180min, Azure intermediate 60min + advanced 180min, AWS intermediate + advanced with `expected_duration_minutes = NULL`, admin sets later). No longer seed-only: `POST /admin/cyber-ranges` lets an instructor create a new entry (an environment's registration flow does this automatically — see `CLAUDE/api.md`). **`is_active`** (default `1`) controls whether `GET /cyber-ranges` (the picker used by the Instructor dashboard's assign/switch-scenario `<select>` and Topology Admin's range picker) returns it — there is deliberately **no DELETE endpoint** for this table: `team_cyber_range_progress`/`documentation_entries` FK to it `NOT NULL` with `PRAGMA foreign_keys = ON` enforced, so a range with real history can't be deleted without destroying that history (SQLite will refuse with a FK constraint error). To retire a range from the pickers, set `is_active = 0` instead — it stays fully intact for any existing join (dashboard, history, debrief). The 5 originally-seeded example ranges were retired this way once real instructor-created ranges replaced them as the intended catalog source.
- `team_cyber_range_progress` — one row per (team, cyber_range), tracks live status/timing. This is where "which range is a team currently doing, and how much time is left" lives — NOT on `teams` or `cyber_ranges` directly, because a team's progress is per-run state.
- `scores` — instructor-awarded points. `student_user_id` nullable = team-level award; `documentation_entry_id` nullable = standalone scoring event not tied to a specific doc entry. **There is no separate `milestones` table** — the PRD's US-007 replaced automatic milestones with free-form instructor scoring directly on student documentation (individual + team attribution). Leaderboard/individual/team totals are always **computed** (`SUM(points) GROUP BY ...`), never stored redundantly.
- `users.password` is **plaintext, by explicit decision** — this is a low-stakes internal training tool, not public-internet-facing. Do not "fix" this into a hashed scheme without checking with the user first; it was an explicit tradeoff, not an oversight.
- `auth_tokens` — opaque bearer tokens (not sessions/cookies), looked up by `server/src/middleware/auth.ts`.
- `credentials` / `cloud_environments` / `cyber_range_environments` / `audit_log` / `environment_discovery_runs` — live cloud environment integration (Phase 1: registration + connectivity check; Phase 2: Azure Resource Graph discovery -> topology; see `PROGRESS.txt` and `C:\Users\Liram\.claude\plans\rustling-seeking-wave.md` for the full multi-phase design). `credentials.secret_ciphertext` is AES-256-GCM encrypted (`server/src/services/credential.service.ts`, key from `CREDENTIAL_MASTER_KEY`) and is the only place a cloud Service Principal (or future VM login) secret is stored — never selected into any API response, see `CLAUDE/invariants.md`. All five are CONFIG despite `created_by_username`/`actor_username`/`triggered_by_username` looking like they "should" be a `users` FK — they're denormalized text snapshots instead, because `users` is a RUN table and a CONFIG table must never FK into RUN. `environment_discovery_runs` has a partial unique index (`WHERE status IN ('queued','running')`) enforcing at most one in-flight run per environment — `discovery.service.ts` relies on the resulting UNIQUE-constraint error to answer a concurrent trigger with 409, not app-level locking.
- **Discovered topology**: `topology_nodes`/`topology_edges` gained `environment_id`/`discovery_run_id` (both nullable — NULL means today's hand-drawn nodes, untouched by discovery) and edges gained `external_key`/`relation_type`. A discovery run upserts by `(cyber_range_id, external_key)` — `external_key` is the full Azure ARM resource id for discovered rows, globally unique and stable across re-runs, so re-discovery updates in place instead of duplicating. **Upsert gotcha**: because the unique index is partial (`WHERE external_key IS NOT NULL`), the `ON CONFLICT` clause must repeat that `WHERE` exactly (`ON CONFLICT (cyber_range_id, external_key) WHERE external_key IS NOT NULL DO UPDATE ...`) or SQLite raises "ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint" — found live while implementing `discovery.service.ts#upsertForCyberRange`. Stale nodes/edges (not touched by the current run) are pruned only after a fully `succeeded` run, never after `partial_failure` — see `discovery.service.ts#pruneStale`.
- **Logical topology redesign** (2026-09-10, see `C:\Users\Liram\.claude\plans\azure-swirling-mitten.md`): the topology represents the *cyber-range exercise*, not a raw Azure resource mirror. **`topology_zones`** is the visual grouping container (DMZ/Internal/SOC/...); a vnet's subnets become zone rows (`external_key` = subnet ARM id) instead of `vnet`/`subnet` topology_nodes rows — those two node_types are no longer produced by discovery. `topology_nodes.zone_id` (FK, nullable) places a node in a zone; `role` is the inferred/instructor-set cyber-exercise role (`domain_controller`, `kali_attacker`, `siem`, `web_server`, `firewall`, `internet_gateway`, ...) used for icon/label instead of the raw Azure type; `is_visible_to_students` (default computed per node_type — only `vm` defaults visible, all other Azure-discovered types like `nic`/`nsg`/`public_ip`/`storage_account`/`key_vault` default hidden) is enforced **server-side** in `topology.routes.ts`'s GET, not just hidden client-side — a student's response never even contains a hidden node's id, and edges touching a hidden node are filtered out too. `status` is instructor-set for now (no live Azure power-state sync yet — a documented future enhancement). **Write-once-then-preserved on re-discovery**: `zone_id`, `role`, `status`, and a zone's `name` are only set on first INSERT (omitted from every `ON CONFLICT ... DO UPDATE` SET clause), same pattern as `pos_x`/`pos_y`, so an instructor's manual corrections survive every later re-discovery run. `topology_edges.from_zone_id`/`to_zone_id` let an edge endpoint be a zone instead of a node (e.g. instructor-drawn `Internet -> Firewall -> Zone`); a `CHECK` on each side enforces exactly one of (node, zone) is set. Deleting a zone (`DELETE /admin/cyber-ranges/:id/topology/zones/:zoneId`) un-assigns its nodes (`zone_id = NULL`) rather than deleting them; `pruneStale` NULLs any surviving node's `zone_id` before deleting a stale zone, to avoid a dangling FK under `PRAGMA foreign_keys = ON`.
- **`access_targets`** (CONFIG) / **`access_sessions`** (RUN) — Phase 4, the student browser-access broker (`server/src/services/accessBroker/`), **now Azure Bastion Shareable Link + Key Vault-backed (Phase 2 of the topology redesign, 2026-09-10)** — replaces the earlier Guacamole-lite token stub, which minted tokens/tracked sessions but never had a real gateway deployed (`wsUrl` was always `null`). `access_targets.topology_node_id` is `UNIQUE`, one row per connectable node. `key_vault_secret_name` (nullable, additive) is the current path: when set, the VM login password lives in the owning `cloud_environments.key_vault_uri`'s Key Vault (`keyVaultCredential.service.ts`), not locally; `username` (plain text — usernames aren't secret) sits alongside it. The older `credential_id` (local AES-256-GCM, `credential.service.ts`) still exists on the table for any pre-Phase-2 rows but new saves always go through Key Vault. Bastion Connect only works for a real Azure-discovered `vm` node (`topology_nodes.environment_id` set) with the owning `cloud_environments.bastion_host_id` populated — a hand-drawn manual node has no real network path to broker and is rejected with `not_connectable`/`bastion_unavailable`. `access_sessions` follows the same RUN-FKs-CONFIG pattern as `help_requests`/`scores`; a summary of every request/deny/end is *also* written to the CONFIG-scoped `audit_log` at the same time, so the compliance trail survives an event reset even though the richer `access_sessions` row doesn't — a deliberate choice, not an oversight (see `CLAUDE/invariants.md`). `access_sessions.broker_connection_id` is unused since this redesign (kept, not dropped, for old rows). Deleting a `topology_nodes` row cleans up its `access_targets` row first (same FK-ordering lesson as `deleteEnvironment` — see the Phase 2 entry above); it deliberately does **not** clean up historical `access_sessions` rows, so a node with real access history can't be silently deleted out from under its own audit trail.
- **`cloud_environments.bastion_host_id`/`key_vault_uri`** (additive, nullable) — auto-populated by discovery (first `microsoft.network/bastionhosts` / `microsoft.keyvault/vaults` resource found in the environment's scope — see `azureDiscoveryProvider.ts`), never instructor-entered; `COALESCE`-preserved across re-discovery runs that don't find one (e.g. a resource-group-scoped query that happens to miss it), same "don't destroy known info" precedent as elsewhere in discovery.
- **`scripts`** (CONFIG) / **`script_executions`** (RUN) — Phase 3, instructor "Run Script" (Azure VM Run Command, `server/src/services/scriptExecution.service.ts`), extended into a full Script Library per the 2026-09-10 follow-up spec. `scripts` is a **global, cyber-range-agnostic catalog** (no `cyber_range_id` column) — an instructor curates it once and reuses entries across ranges/cohorts, same reasoning as `cyber_ranges` itself; `category` is free text (UI offers suggestions — Normal/Suspicious Activity, Investigation, AI/Azure/AWS Activity, Cleanup — never a fixed enum). `script_executions.script_id` is nullable (`ON DELETE SET NULL`) — a "write manually, don't save" run has no library row at all. **`script_executions` deliberately has no `script_content`/`script_text` column** — per the approved topology-redesign plan (a script may embed credentials/tokens an instructor is testing against), only a SHA-256 `script_hash` plus safe, truncated `output_excerpt`/`error_text` are persisted; the actual content of a *library* run remains recoverable via `script_id -> scripts.content` for as long as that library entry exists, while an ad hoc run's content is gone once run (by design, not an oversight). A run is validated against the target VM's discovered `osType` (`Windows` -> `powershell`, `Linux` -> `bash`) before ever calling Azure — a mismatched script type is rejected with `reason: 'os_mismatch'`, never silently coerced. `idx_one_running_script_per_node` (partial unique index, same pattern as `idx_one_active_discovery_run`) enforces at most one `running` execution per node at a time — mirrors Azure's own one-command-at-a-time constraint on a VM. `POST /admin/topology/nodes/:nodeId/run-script` responds immediately (`202 {executionId}`) and runs the actual `ComputeManagementClient.virtualMachines.beginRunCommand` call in the background — Run Command can take minutes for a script meant to produce real, observable activity, far too long to hold an HTTP request open (same reasoning as the async discovery-run pattern). Needs the new custom RBAC role `docs/azure/cyber-range-vm-run-command-role.json` (`Microsoft.Compute/virtualMachines/{read,runCommand/action,runCommands/read}`) assigned to the app's Service Principal in addition to Reader — see `CLAUDE/invariants.md`.

## Seeding

`npm run seed -w server` (idempotent — safe to re-run) applies migrations, then seeds the CONFIG catalog + a demo RUN: 2 teams (Alpha/Bravo), 1 instructor (`instructor`/`instructor123`) and 4 students (`alice`/`bob`/`carol`/`dave`, all `student123`). If an active `event_runs` row already exists, demo team/user seeding is skipped (so re-running seed after real event data exists won't clobber it) — but CONFIG tables always get their `INSERT OR IGNORE` pass.
